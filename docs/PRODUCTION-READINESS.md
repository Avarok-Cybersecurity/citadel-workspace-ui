## Detail

### 1. ILM network loop busy-spins without yielding once the transport's inbound channel closes — on wasm this permanently freezes the tab

**critical** · concurrency · fix cost contained · `citadel-internal-service/intersession-layer-messaging/src/lib.rs:471`

**Failure:** User is logged in with a messenger handle open (the normal state). Any of: logout, tab demoted from leader, the websocket-disconnected teardown handler running after a service drop, or restart() — each calls close_connection, which clears the connections map, dropping MessengerTx. Its Drop removes the sole sender for the ILM's inbound channel; the leaked ILM network loop's recv() then returns Ready(None) synchronously in an infinite loop with no yield. In the browser the JS thread never regains control: the tab hard-freezes and the teardown/restart that triggered it never completes.

**Why it survived refutation:** I tried to refute this three ways and failed. (1) Sender lifetime: create_ipc_handles (connector messenger/mod.rs:1042) makes exactly one sender for the ISM inbound channel; multiplex (mod.rs:323) clones it into txs_to_inbound and drops the original at end of multiplex; MessengerTx::Drop (mod.rs:805-813) removes the map clone — after that the channel is closed, and next_message (mod.rs:1075-1081) is a bare recv().await that returns Ready(None) synchronously. No other lasting clone exists (the network_inbound_task at mod.rs:486 only borrows from the map transiently). (2) Loop stop: network_io_handle (ILM lib.rs:471-479) is `loop { if !can_run() break; process_next_network_message().await }` with no sleep, unlike its outbound/inbound siblings which interleave platform_sleep; process_next_network_message (lib.rs:979) does nothing on None; can_run() (lib.rs:1304) reads is_running, which only shutdown() clears, and grep confirms no .shutdown( caller anywhere in the connector or wasm client. (3) Trigger reachability: close_connection (wasm lib.rs:928-942) does connections.clear(), dropping the Arc<MessengerTx> (all other clones, e.g. lib.rs:826, are transient send-path clones), and close_connection is invoked from the websocket-disconnected teardown handler (leader-socket-teardown.ts:60), leader demotion (closeLeaderSocket, :88), auth disconnect (auth.ts:102), and restart(). On wasm the ILM background task runs under wasm_bindgen_futures::spawn_local; a poll that loops on Ready(None) forever never returns to the JS event loop, so the thread freezes; on native it pins a tokio worker at 100%.

**Fix:** In process_next_network_message, treat None from self.network.next_message() as transport-closed: return a signal the loop breaks on (or call self.toggle_off()), so the four loops exit; at minimum add platform_sleep(INBOUND_POLL) in the None arm so the loop always yields. Pair with a real shutdown path for finding 5.

### 2. add_user_to_domain runs its last-admin check after releasing the lock the contract requires

**high** · concurrency · fix cost contained · `citadel-workspace-server-kernel/src/handlers/domain/server_ops/async_domain_server_ops.rs:352`

**Failure:** Admins A and B each issue AddMember{user_id: <the other admin>, role: Member} concurrently from two connections (the ordinary Add-member dialog accepts an existing admin's name). Both ensure_not_last_admin calls count 2 admins before either insert_user lands, both pass, both role writes land, and the workspace reaches zero admins — a state promotion cannot recover from, because promotion requires an admin. The same unlocked window also lets AddMember race update_workspace_member_role and remove_user_from_domain, whose lock only excludes participants.

**Why it survived refutation:** Tried to refute by looking for a lock in the caller and by checking whether commands are serialized. Neither holds: the AddMember arm of async_process_command.rs (line 260-271) takes no lock, and the kernel spawns one task per connection (async_kernel.rs:1237) with commands awaited inline per connection — so two admins on two connections genuinely interleave. In the handler itself, `_workspace_guard` (line 282) is scoped inside the `if domain_id == WORKSPACE_ROOT_ID` branch and drops at that branch's end; `ensure_not_last_admin` (line 352) and `insert_user` (line 359-361) run lock-free. tests/last_admin_race_test.rs:115-118 explicitly admits this ("add_user_to_domain's guard is scoped to its root branch and has dropped by the time the demote check runs") and its writer list (lines 136-139) covers only the other two role writers, so the source-assertion gate does not pin this function. The codebase's own docs call zero admins unrecoverable.

**Fix:** Acquire lock_workspaces at the top of add_user_to_domain (before the root/node branch) and hold it through ensure_not_last_admin, the role write, and insert_user; then add "async fn add_user_to_domain" to the writer list in every_role_writer_holds_the_workspace_lock. Verify lock ordering with the lock_nodes taken in the non-root branch stays consistent with other holders (tokio Mutex is non-reentrant; the two are distinct mutexes, and no existing path takes them in the opposite order).

### 3. After a gap-patience out-of-order delivery, the late-arriving missing message is classified 'already delivered', re-ACKed and cleared — the application never receives it

**high** · data-loss · fix cost contained · `citadel-internal-service/intersession-layer-messaging/src/lib.rs:878`

**Failure:** Sender's msg N is stuck >20s (the known BLOCKED-RECOVERY stall shape) while N+1 already arrived and is held. At 20s the receiver delivers N+1 out of order and advances the frontier to N+1. When the stall clears and N finally arrives, the line-878 branch classifies it as already delivered, re-ACKs it, and clears it from the backend. The user permanently loses message N — a chat message or revfs operation — while both sides' logs show it sent, ACKed, and 'already delivered'.

**Why it survived refutation:** Confirmed by reading the full inbound path. held_too_long (message_tracker.rs:328-341) fires after GAP_PATIENCE_SECS=20 (lib.rs:315); the branch at lib.rs:921-933 then falls through and delivers N+1 out of order, and mark_delivered (lib.rs:943, tracker :355-376) advances last_delivered to N+1 — over the undelivered hole at N. Nothing records the skipped id. When N later arrives, the guard at lib.rs:878 asks only safe_to_ack (tracker :347-352, `msg_id <= frontier`), which is now true for N, so N is re-ACKed and cleared from the backend (lib.rs:885-899) without delivery.deliver() ever running. I looked for a refutation in the tests: a_window_never_delivers_out_of_order.rs pins the contiguity/hold behavior but never exercises the 20s patience expiry followed by late arrival, so nothing pins the correct behavior here. The code's own comment ('the sender will never send it again') shows the skip was designed for a permanently unproducible id — but the trigger shape the codebase actually has (known head-of-line stall where BLOCKED-RECOVERY eventually releases the head after >20s) produces a LATE id, not a dead one, and the receiver then actively destroys it. SEND_WINDOW=8 means multiple messages are legitimately in flight, so the N-missing/N+1-held state is a normal occurrence; only the 20s persistence is pathological, and known problem 2 makes exactly that real.

**Fix:** When held_too_long forces an out-of-order delivery, record the skipped ids in a per-peer skipped set (persisted with the tracker); in the line-878 branch, if the id is <= frontier but in the skipped set, deliver it (late, out of order — strictly better than silent loss) and remove it from the set, instead of discarding.

### 4. Dropping an ILM never stops its four background loops: the Drop guard's condition can never be true while they run, and its signal would not stop them anyway

**high** · robustness · fix cost contained · `citadel-internal-service/intersession-layer-messaging/src/lib.rs:356`

**Failure:** Every WASM-client restart/close (or any native consumer dropping a MessengerTx) drops the ILM; its Drop is a no-op, so the outbound/inbound/network/peer-polling loops keep running forever against the abandoned per-CID backend — polling every 200ms, logging errors, and syncing stale tracker state to the same durable keys the replacement ILM for that CID uses, which can corrupt resync/BLOCKED-RECOVERY bookkeeping of the live instance. On wasm the leaked network loop additionally becomes the finding-2 hot spin.

**Why it survived refutation:** Verified all three legs. (1) The Drop at lib.rs:355-360 requires Arc::strong_count(&self.is_running) == 1, but during any external drop self holds one count and the background task's clone_internal (lib.rs:393-407, captured at :414) holds another, so the count is >= 2 and the branch is dead unless the task already exited. (2) Even if it fired, poll_outbound_tx.send(()) is consumed by the outbound loop (lib.rs:426-441) as a poll nudge — the loop breaks only on !can_run() (is_running, cleared only by toggle_off, called only from shutdown() at :1240 and the post-select shutdown hook at :1525-ish after a loop already ended) — and recv() can never return None because the task's own clone holds the senders. (3) grep confirms no .shutdown( caller in the connector or wasm client; MessengerTx owns the ILM directly (mod.rs:802, Option<CitadelWorkspaceISM>, not shared), so every MessengerTx drop (connections.clear() at wasm lib.rs:942 on close/restart) leaks the four loops with their Arc'd backend, tracker and ISMHandle. The leaked tracker does share durable per-CID backend keys ('last_delivered', 'last_sent', 'last_acked') with any replacement ILM for the same CID, so concurrent sync_backend writes from the zombie can clobber the live instance's state. Note the acute wasm consequence is finding 2's spin (the leaked network loop on a closed channel); this finding is the root cause plus the native-side leak.

**Fix:** Give the background task a dedicated shutdown signal: store a oneshot (or set is_running via an explicit toggle_off) in Drop when the last external handle goes — with the task holding one clone, the correct Drop condition is strong_count == 2; simpler and more robust, have MessengerTx::Drop call ism.toggle_off() (expose it), so the loops exit within one poll cycle.

### 5. Congestion-ladder reconfigure clobbers the chosen video profile on the first frame

**high** · correctness · fix cost contained · `citadel-workspaces/src/lib/call/media-pipeline.ts:121`

**Failure:** Start any screen share (1920x1080@8 profile), or pick Balanced (854x480@24) or Data saver (640x360@15) in the video settings and start a video call. The first encoded frame reconfigures the encoder to width=profile.width but height=720, framerate=30, discarding the initial correct configure at line 101 before a single frame is sent. The screen encoder becomes 1920x720@30 — vertically squashed (Chromium scales input frames to the configured size), unreadable text, ~4x the intended frame rate at unchanged bitrate; saver camera becomes 640x720@30 at 250kbps. Only the default 1280x720@30 camera profile escapes, because it happens to equal QUALITY_LADDER[0].

**Why it survived refutation:** Tried to refute via a guard or profile-aware ladder: none exists. appliedRung starts at -1 (line 111) and every CongestionState starts at rung 0 (INITIAL_CONGESTION in congestion.ts:105), so the branch at line 121 fires on the very first encode() and configures {width: profile.width, height: level.height=720, framerate: level.framerate=30}. Verified the profiles: VIDEO_PROFILE_SCREEN is 1920x1080@8 (codec-support.ts:77), balanced camera 854x480@24, saver 640x360@15 (video-quality-profiles.ts). allowsAdaptation only freezes congestion mutation, not this first-frame reconfigure — rung stays 0, which still differs from -1. Also verified SendEncoder.encodeScreen (send-encoder.ts:162) passes the shared this.congestion into the screen encoder, so in auto mode later rung changes apply camera ladder heights (540/360/240) to the 1920-wide screen, contradicting encodeScreen's own comment that the two must not share congestion behaviour. No test covers this: media-pipeline.ts is the module documented as untestable in jsdom, and congestion.test.ts only tests the ladder math.

**Fix:** Initialize appliedRung to 0 so rung 0 never reconfigures away from the initial profile configure, and derive rung configs from the profile: scale width proportionally (width = round(profile.width * level.height / profile.height), even) and use min(profile.framerate, level.framerate). Additionally give the screen encoder its own congestion state (or pin it to rung 0) in SendEncoder.encodeScreen.

### 6. First screen-share frame never fires onStreamsChanged, so a remote share can stay invisible

**high** · ux · fix cost trivial · `citadel-workspaces/src/lib/call/receiver-pool.ts:86`

**Failure:** Peer starts sharing mid-call. Their CallMediaState(screen:true) arrives and recomputes the context while getRemoteScreenStreams() is still empty, so useStageShare returns share:null. The first screen frame then creates the screenSink, but accept() never calls onStreamsChanged for a screen appearance, so streamsVersion never bumps and the memo never recomputes. The viewer sees no share until some unrelated state transition (mic toggle, participant change, quality classification change) — potentially never in a quiet call. If the frame happens to beat the CallMediaState, it works, making this an intermittent, order-dependent failure.

**Why it survived refutation:** Tried to refute three ways. (1) Maybe accept() sees the screen via getVideoStream(): no — acceptScreen builds a separate screenSink (peer-receiver.ts:103) reachable only through getScreenStream(); lines 79-88 check only hadVideo/hadAudio. (2) Maybe the UI re-reads streams every render: no — buildCallContext snapshots session.getRemoteScreenStreams() inside CallProvider's useMemo (build-call-context.ts:53, CallProvider.tsx:226), whose deps are call/streamsVersion/qualities/...; a new Map is only produced when that memo recomputes, and useStageShare memoizes on that same Map reference. (3) Maybe the 2s quality poll re-renders: only when a peer's quality CLASSIFICATION changes (sameQualities guard, CallProvider.tsx:216); in an established call it sits at 'good' and compares equal.
